# 식사 기록 선택적 연동 삭제 계획

상태: `feat/meal-history-linked-delete` worktree에서 구현 완료. 기존 스크린샷 모드 변경은 원래 작업 폴더에 보존하며 이 브랜치에는 포함하지 않는다. 아래 2절은 구현 전 구조 조사이며, 구현 검증 결과는 10절에 기록한다.

## 1. 목적과 확정 정책

- 삭제 확인창에서 사용자가 `기록만 삭제` 또는 `이 식사로 받은 스티커도 함께 삭제`를 선택한다. 체크박스 기본값은 해제이며 이전 선택을 저장하지 않는다.
- 이미 사용한 보상은 상태·스티커 칸·사용 날짜까지 그대로 보존한다. 보관함 수량은 별도 누적 수집량이므로 연동 삭제 시 차감한다.
- 기록만 삭제한 건은 나중에 연동 삭제할 수 없다. 과거에 삭제한 기록을 추정하여 소급 정리하지 않는다.
- 스크린샷 모드의 고정 표시와 실제 데이터는 별개다. 삭제 검증은 일반 모드에서 수행한다.

## 2. 코드에서 확인한 현재 구조

- `LocalMealProgressService.deleteMealHistoryEntry()`는 history만 변경하며 저장 성공 여부를 확인하지 않는다. 기존 테스트는 보관함과 보상판 유지를 명시한다.
- 식사 기록의 `rewardIds`로 수집량을 차감하고, `RewardGoalSlot.mealSessionId`로 해당 보상 칸을 정확히 찾을 수 있다. 한 식사는 여러 진행 중 보상판을 동시에 채운다.
- 완료 저장은 `_withPreferences` 직렬 큐와 `mealCompletionJournal`의 최종 스냅샷 재적용으로 복구한다. 저널에는 history/inventory/active/earned가 들어가며 used는 없다.
- `_loadActiveRewardGoals()`의 `take(2)`는 복귀한 보상판을 누락시킬 수 있다. 생성은 서비스와 화면 모두 2개 제한을 검사한다.
- 홈은 이미 `RouteAware.didPopNext()`에서 갱신한다. 추가 갱신 로직을 먼저 넣지 않고 실제 Navigator/RouteObserver 구성을 사용하는 테스트로 검증한다.
- 홈/타이머 완료 복구는 `recordMealResult()` 후 별도 active-session 저장소를 지운다. 이 삭제가 실패하면 완료 재시도가 남을 수 있다.

## 3. 사용자 흐름

1. 휴지통을 누르면 기본 해제된 체크박스가 있는 삭제 확인창을 연다.
2. 설명: `함께 삭제하면 스티커 보관함과 보상판에서도 차감돼요. 아직 사용하지 않은 보상은 달성이 취소될 수 있어요. 이미 사용한 보상은 유지돼요.`
3. 기록만 삭제 시에도 다시 연동 삭제할 수 없다는 짧은 설명을 제공한다.
4. `rewardIds`가 비어 있고 연결된 미사용 보상 칸도 없으면 선택 항목을 숨긴다. 오래된 데이터에서 rewardIds가 비어도 연결 칸이 있으면 선택 가능하게 한다. 확인창 준비에 실패하면 삭제를 진행하지 않고 재시도를 안내한다.
5. 취소·뒤로가기·바깥 터치는 변경 없이 종료한다. 실행 중에는 중복 확인창과 중복 삭제를 막는다.
6. 성공 후 기록 목록을 다시 읽는다. 이미 삭제된 ID는 추가 차감 없이 목록을 갱신한다.
7. 저장 오류는 성공으로 표시하지 않는다. 저널이 이미 저장됐을 수 있으므로 `저장을 완료하지 못했어요. 다시 시도해 주세요.`처럼 결과 미확정 상태를 설명한다. 재시도는 먼저 복구 후 최신 목록을 읽고, 남은 대상에만 삭제를 적용한다.
8. 한국어·영어·일본어·스페인어·브라질 포르투갈어에 체크박스, 달성 취소/사용 완료 유지 안내, 실패/복구 대기 문구를 추가한다. 작은 화면·큰 글씨는 스크롤 가능한 확인창으로 대응한다.

## 4. 서비스 변경 알고리즘

API는 기존 호출과 호환되도록 `deleteMealHistoryEntry(String entryId, {bool deleteLinkedRewards = false})` 형태를 유지한다. 반환 bool은 대상 존재 여부, 실패는 예외로 구분한다.

1. 기존 큐에서 완료 저널 복구를 마친 다음 저장소 원본을 읽는다. 화면용 `loadSnapshot()`/스크린샷 inventory를 계산 입력으로 쓰지 않는다.
2. 대상이 없으면 false. 두 삭제 방식 모두 대상 ID를 `deletedMealSessionIds`에 추가한다. 이 목록은 progress 큐에서만 읽고 쓰며, 완료 재실행 방지를 위해 임의의 개수/기간 제한으로 제거하지 않는다. 식사 내용·사진·보상 문구는 저장하지 않고 ID만 보존한다.
3. 기록만 삭제는 기존 inventory/active/earned를 변경하지 않는다.
4. 연동 삭제는 대상 기록의 rewardIds 빈도만큼 해당 inventory 항목을 차감한다. 없는 항목은 건너뛰고 0 이하가 되면 항목을 제거한다. 알 수 없는 reward ID도 저장된 ID로 매칭하며 현재 카탈로그에 없다는 이유로 제외하지 않는다. 남은 기록 전체로 inventory를 재계산하지 않는다.
5. 모든 active/earned 보상판에서 mealSessionId가 일치하는 칸만 제거한다. 다른 식사의 칸, 목표 수량, 이름, 생성일은 보존한다.
6. earned 보상은 삭제 후 filledCount < requiredStickerCount이면 active로 돌리고 earnedAt/readyAt을 명시적으로 null 처리한다. 목표 이상이면 earned를 유지한다. used 목록과 레거시 redeemed 목록은 읽기·쓰기 대상에서 제외한다.
7. 기존 active 순서를 유지하고 복귀한 보상판을 기존 earned 순서대로 뒤에 붙인다. 연동 삭제 전 active/earned 전체에서 중복 goal ID를 검증한다. 충돌이 있으면 해당 연동 삭제 전체를 저널 저장 전에 중단하고 원본을 보존하며 데이터 오류를 안내한다. 임의 병합·덮어쓰기·건너뛰기를 하지 않는다. 기록만 삭제는 보상 ID 충돌 때문에 막지 않는다.
8. history/inventory/active/earned의 변경 후 상태와 삭제 ID 목록을 하나의 완료 저널에 저장한 뒤 복구 함수로 적용한다. 삭제 ID 필드는 선택 필드로 추가하며 예전 저널에는 없어도 복구된다. 필드가 없으면 기존 삭제 ID 키를 지우거나 덮어쓰지 않는다. 필드가 있으면 삭제 ID를 먼저 저장한 뒤 네 목록을 적용하고 마지막에 저널을 지운다. 모든 쓰기의 bool과 저널 제거 실패를 확인한다. 별도 저널·새 DB·의존성·대규모 마이그레이션은 추가하지 않는다.
9. 기록만 삭제에서도 저널 사용으로 실패 복구를 보장한다. 단, 이 경로는 기존 inventory/active/earned 원시 리스트를 보존하여 불필요한 디코딩·재직렬화로 알 수 없는 데이터를 제거하지 않는다. 레거시 active 데이터가 있을 때에는 저널이 레거시 키를 제거하므로 기존 로더의 의미를 유지해 active/earned로 변환하는 경우를 테스트한다.

완료 재시도 정책: `recordMealResult`는 같은 progress 큐에서 저널 복구 후, 기록 생성/보상 지급 전에 삭제 ID를 검사한다. ID 계산은 기존과 동일하게 `result.sessionId ?? result.endedAt.microsecondsSinceEpoch.toString()`를 사용한다. 삭제된 ID이면 저장을 수행하지 않고 전용 `DeletedMealSessionException`으로 종료한다. 일반 저장 실패와 분리한다.

- 홈 복구: 전용 예외이면 남은 active session을 정리하고 최신 진행 상태를 읽는다. clear 실패는 기존 복구 실패로 처리하고 재시도해도 보상은 지급하지 않는다.
- 타이머 완료: 전용 예외이면 active session 정리 후 홈으로 돌아가며 결과/축하 애니메이션을 열지 않는다. clear 실패 시에는 완료를 다시 기록하지 않는 정리 재시도를 제공한다.
- 결과 화면의 직접 recordMealResult fallback: 전용 예외는 저장 재시도나 보상 애니메이션으로 이어지지 않게 처리하고 홈 이동을 제공한다. 이미 전달된 RecordedMealSession은 저장을 재호출하지 않음을 테스트한다.
- 삭제 ID 저장 형식은 StringList다. 키가 없을 때만 빈 목록으로 해석하고, 중복된 정상 ID는 집합으로 처리한다. 잘못된 타입·빈 ID·읽기 실패는 빈 목록으로 대체하지 않으며 완료 저장/삭제를 전용 데이터 오류로 중단하고 기존 값을 보존한다. 정상적인 읽기 전용 snapshot은 이 키를 읽지 않아 계속 조회할 수 있다. 별도 자동 초기화는 하지 않는다. 오류 문구는 단순 재시도로 해결된다고 약속하지 않고 저장 데이터를 확인해야 함을 안내한다.
- 저널의 선택 삭제 ID 필드도 어떤 쓰기보다 먼저 형식 검증한다. 필드 손상은 저널과 데이터 원본을 보존하고 복구 오류를 표시한다. 복구가 필요한 동안에는 진행 상태의 일관성을 보장할 수 없으므로 저장/삭제를 진행하지 않는다. 정상 저널이 있는 경우 먼저 복구하여 손상된 삭제 ID 키를 정상 스냅샷으로 대체할 수 있다.
- 이 변경은 기본 기록만 삭제에도 적용한다. 삭제 후 오래된 완료 요청이 도착하는 순서를 명시적으로 테스트한다. 중복 판정용 ID 목록의 장기 증가 비용은 허용하되, 실제 식사 횟수 규모의 데이터로 로드/저장 비용을 확인한다.
- 새 키는 이전 앱에서 무시되므로 삭제 ID를 모르는 구버전으로 바이너리를 되돌린 뒤 완료 재시도를 수행하는 상황까지 보장하지 않는다. 다운그레이드 시의 데이터 정리는 이번 범위에서 수행하지 않는다.

## 5. 보상판 2개 제한과 화면 정책

- 신규 생성 제한은 계속 2개다. 달성 취소에 의한 복귀는 예외적으로 3개 이상 허용한다.
- 기존 생성·완료·수정·레거시 저장 경로가 정상 데이터에서 최대 2개를 지켰는지 확인한다. 이미 3개 이상인 raw active fixture도 읽기/저장 왕복 시 전부 보존하는 것으로 명시하며, 개수만으로 정당한 보상판을 삭제하거나 숨기지 않는다. 로더의 `take(maxActiveRewardGoals)`를 제거하고 실제 active를 모두 보존한다. 취소·수정·저장·앱 재시작에서도 초과분이 사라지지 않아야 한다.
- 2개 이상이면 신규 생성은 차단한다. 다음 식사에서는 복귀한 보상판을 포함한 모든 active가 기존 규칙대로 한 칸씩 채워진다. 이 동작을 의도된 정책으로 테스트한다.
- 보상 화면에는 전체 목록을 표시한다. 홈은 현재처럼 2개까지만 요약하되 초과 시 `외 N개` 표시를 추가하여 숨겨진 보상판의 존재를 알린다. 미니 보상판은 기존 첫 번째 항목을 유지한다.
- 생성 제한 안내는 3개 이상 복귀 상황에서도 모순되지 않도록 `새 보상 약속은 진행 중인 약속이 2개 미만일 때 만들 수 있어요.`라는 의미로 조정한다.
- 기존 `used` 보상판과 보관함 개수가 다를 수 있음은 사용 완료 이력 보존 정책에 따른 정상 상태다.

## 6. 구현 순서와 변경 범위

1. 서비스 테스트부터 추가: 기존 기록만 삭제 계약을 보존하고 연동 차감·보상 복귀·저널 복구를 검증한다.
2. `local_meal_progress_service.dart`의 삭제·로더·저널 선택 필드·삭제 ID 차단을 수정하고 전용 예외를 추가한다. home/timer/result의 완료 호출부에서 삭제 완료 예외를 구분한다. 삭제되지 않은 식사의 보상 지급 규칙은 유지한다.
3. `meal_history_screen.dart`에 선택/진행 중/오류 처리를 추가한다. 미사용 연결 칸 확인용 서비스 helper는 삭제와 동일한 progress 큐·저널 복구·전체 active/earned/레거시 로더를 사용한다. UI가 직접 SharedPreferences를 읽거나 일부 보상판만 검사하지 않는다. 최종 삭제는 항상 최신 상태로 다시 계산한다.
4. `home_screen.dart` 초과 보상 요약과 `reward_goal_screen.dart` 생성 제한 안내를 필요한 범위에서 조정한다. RouteAware 갱신은 유지한다.
5. `text_sets.dart`와 5개 언어의 meal_history/rewards/home 텍스트를 갱신한다.
6. 관련 테스트와 정적 분석 후 실기기 확인한다. 버전·빌드 번호·IAP·서명·배포 설정은 변경하지 않는다.

## 7. 필수 검증

### 서비스 회귀
- 옵션 미지정/false: 기록만 삭제, inventory/active/earned/used 유지. 취득 이력이 없는 항목도 보존.
- true: 동일 차량 여러 식사에서 1개만 차감, 마지막 1개 삭제 시 항목 제거, 미완료 식사·빈 rewardIds·없는 inventory·알 수 없는 ID·중복 rewardIds·없는 entryId.
- 동일 식사에 연결된 여러 active/earned 칸 모두 제거. 무관한 칸 유지. used 및 레거시 redeemed 원시 값은 전후 동일.
- earned가 목표 미달이면 복귀, 날짜 초기화; 목표 이상이면 유지. 목표 수량 수정 후 삭제도 확인.
- 이미 active 2개일 때 여러 earned 복귀, 재시작/수정/취소/다음 식사에도 초과분 보존, 신규 생성 차단 및 2개 미만에서 재허용.
- 중복 탭/직렬 동시 삭제/재시도에서 한 번만 차감. 완료 저장과 삭제의 순서를 달리해 최종 상태를 확인.
- 저널 저장, 각 데이터 키 저장, 레거시 키 제거, 저널 제거 단계별 false/예외 주입. 새 서비스로 복구 시 최종 상태 일치 및 중복 차감 없음. 기존 완료 저널도 이전과 동일하게 복구.
- 기록만 삭제의 원시 데이터 유지, 레거시 active/earned 마이그레이션, 사용 보상 보존.

- 삭제 ID 키 없음/중복 정상 ID/잘못된 타입/빈 ID/읽기 실패를 구분한다. 손상 시 완료 저장·삭제가 원본을 덮어쓰지 않고 조회는 가능함을 확인한다. 손상된 저널 필드는 첫 쓰기 전에 오류 처리하며 원본 보존. 정상 저널로 삭제 ID 키 복구 가능.
- active/earned 내부 및 상호 중복 ID에서 연동 삭제 전체 무변경·오류 안내, 기록만 삭제는 영향 없음.
- 삭제 ID 필드 없는 기존 저널 복구가 기존 삭제 ID 목록을 보존함. 삭제 ID 저장 단계 실패·저널 적용 도중 재시작도 일관성 유지. sessionId가 없는 레거시 결과의 동일 ID 계산. 삭제 ID 누적 시 실제 사용량 규모의 저장 비용.
